# Architecture Review
Generated: 2026-08-17T16:40:09.868Z
Score: 45/100

## Summary
The active React/Router app (App→Home/ChallengeDetail/Result→lib/challenge,points→types) is small, pure-function-friendly, and free of circular imports, but it coexists with a large amount of disconnected scaffolding: a full localStorage persistence layer (db.ts/schema.ts) and a generated contract file (contract.ts) that define a second, incompatible `Challenge` model and dozens of functions nothing calls. As a result the app's actual behavior — computing a streak/reward and navigating to a result screen — never persists anything, even though the persistence code to do so already exists unused, which is a real functional/architectural gap, not just clutter.

## Issues
### Critical
- [duplication] `Challenge` is declared twice with completely incompatible shapes: types/index.ts defines {id,title,challengeGoal,targetDays,progress,streak,badgesEarned,...} while lib/contract.ts defines {id,name,description,targetPoints,startDate,endDate,status}. Any code importing both (or a future contributor following contract.ts) will collide with the real domain model actually used by the app. — Files: src/types/index.ts, src/lib/contract.ts / Fix: Delete or clearly quarantine contract.ts (rename its types, e.g. `ContractChallenge`) and make types/index.ts the single source of truth for domain types; if contract.ts is generated from an external spec that's no longer authoritative, remove it from the build.
- [dead_code] lib/contract.ts exports ~12 types/function signatures (getChallengeByIdFn, listChallengesFn, getUserPointsFn, recordChallengeCompletionFn, calculatePointsFn, formatPointsDisplayFn, PolicyViolation, validatePoliciesFn, ComplianceCheckResult, verifyComplianceFn, UserPoints, ChallengeProgress) — none are imported anywhere in the 13 files. It reads as an auto-generated cross-package contract from a different (Next.js-style `challenge/[id]/page.tsx`) architecture than the one actually implemented (Vite/react-router). — Files: src/lib/contract.ts / Fix: Confirm whether any other package/repo still depends on this contract; if not, delete it. If it is load-bearing for codegen, move it out of `lib/` into a dedicated `contracts/` folder and exclude it from app type-checking to avoid clashing with real types.
- [consistency] The app's only real feature (record a challenge's progress/streak) is never persisted: Home/ChallengeDetail read from the in-memory `seedChallenges` array and ChallengeDetail's handleVerify only forwards computed values via router `location.state` to Result. Meanwhile lib/db.ts (challengeStore.upsert) and lib/challenge.ts (updateProgress, awardBadge) implement exactly the persistence path needed but are never called from any page, so a full localStorage-backed data layer sits completely disconnected from the UI. — Files: src/pages/ChallengeDetail.tsx, src/lib/db.ts, src/lib/challenge.ts / Fix: Wire ChallengeDetail's handleVerify to call `challengeStore.upsert(updateProgress(awardBadge(...)))` (or equivalent) so progress actually survives navigation/reload, or explicitly delete db.ts/schema.ts if this app is intentionally stateless and document that decision.

They implement a points/participant system the UI never touches (Result.tsx recomputes rewards independently via calculateChallengeReward). — Files: src/lib/points.ts, src/lib/db.ts / Fix: Either integrate these into the actual flow (award/persist points when a challenge is verified) or remove them to reduce surface area; if kept for a near-term feature, mark with a TODO referencing the tracking ticket.

There's no redirect/guard for missing state and no shared store, making this the only state-management approach in the app and a fragile one. — Files: src/pages/Result.tsx / Fix: Add a guard that redirects to `/` when required state is missing, or move challenge-in-progress data into a small context/store (or the existing db.ts store) instead of relying on router state.

### Suggestions

- [naming] The domain vocabulary for the same concept diverges across files: types/index.ts uses title/challengeGoal/targetDays/progress/streak while lib/contract.ts uses name/description/targetPoints/startDate/endDate/status for the same 'Challenge' entity, suggesting two unreconciled specs. — Files: src/types/index.ts, src/lib/contract.ts / Fix: Pick one vocabulary as canonical (types/index.ts, since it matches the shipped UI) and delete/rename the other rather than letting both exist under the same type name.
- [structure] lib/contract.ts is explicitly marked as auto-generated ('자동 생성. 수정하지 마라') with a totally different documentation style (Korean, packet references to 'heal-1-01/heal-2-03') than the rest of lib/, yet it's stored alongside hand-written implementation modules. — Files: src/lib/contract.ts / Fix: Isolate generated contracts in their own directory (e.g. src/generated/ or src/contracts/) with a README noting the generation source, or remove them if that generation pipeline is no longer part of this repo.
- [consistency] OnboardingNotice.tsx uses inline `style={{...}}` objects for all layout/typography, while no other component in the codebase shows any styling approach (no CSS modules, no className usage visible) — there's no established, consistent styling convention to follow. — Files: src/components/OnboardingNotice.tsx / Fix: Establish and document one styling approach (CSS modules, Tailwind, styled-components, etc.) and apply it uniformly instead of ad hoc inline styles in a single component.
- [consistency] lib/db.ts's readCollection silently swallows JSON.parse failures (`catch { return [] }`) with no logging, while no other module in the codebase establishes any error-handling convention (try/catch elsewhere is absent) to compare it against. — Files: src/lib/db.ts / Fix: Adopt a small shared error-handling utility (e.g. a `logError` helper) so storage-read failures are at least logged/observable instead of failing silently, and apply the same convention anywhere else storage or I/O is added.
